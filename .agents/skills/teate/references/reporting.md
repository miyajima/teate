# 一次情報の追加調査と日本語レポート

最新情報の調査を依頼された場合に使う。通常はTeateの定型レポートを提示すればよく、この手順を毎回すべて実行する必要はない。

## 情報を集める

1. Teateのフィード差分を入口にする。前回成功以降に48時間を重ね、初回は直近7日を中心に、以前でも悪用継続中の重大案件を確認する。前回成功時刻が不明ならその旨を記し、初回扱いにする。
2. 必要な案件だけCISA KEV、JPCERT/CC、JVN、CVE.org / NVD、製品ベンダーの公式勧告を確認する。利用可能な接続ツールを優先する。取得不能は未確認で、検索結果の要約だけで修正版や悪用を断定しない。
3. 実悪用・KEV・外部公開・認証条件を重視する。PoC公開、攻撃試行、悪用成功を区別する。公開日・更新日・KEV追加日も区別する。利用製品・稼働版・到達可能性は実測か登録情報に基づき、不明は不明とする。
4. 外部の新しい案件は台帳の指摘と分けて「該当未確認」として報告する。外部調査だけでTeateの件数や優先度を変えない。フィード項目の新規件数を、新規脆弱性・新規資産の件数として扱わない。

公式の入口：

- CISA KEV: https://www.cisa.gov/known-exploited-vulnerabilities-catalog
- CISA本体が取得不能なら公式ミラー: https://github.com/cisagov/kev-data
- JPCERT/CC: https://www.jpcert.or.jp/at/
- JVN: https://jvn.jp/
- CVE: https://www.cve.org/
- NVD: https://nvd.nist.gov/vuln/search

取得できた情報と取得できなかった情報を区別する。ブラウザー側で読めても、Teate側の通信が成功したことにはしない。ソースが利用不能でも、別の一次情報で確認可能な範囲は続ける。プロキシやネットワーク設定による制限は回避しない。

## 短く報告する

冒頭に確認日時と対象期間を示す。既定は日本時間で、ユーザー指定があれば従う。

1. Teateの定型レポートと`facts`の件数を提示する。新規・継続・解消の内訳は証跡にあるものだけを使い、未出力は未集計とする。
2. 重要案件は原則5件以内。CVE ID、影響製品・版、悪用状況、優先度の根拠、公式の修正版・暫定策、安全な該当確認と対応後確認、推奨着手目安、公式リンクと公開／更新日を添える。台帳の優先度と、外部調査での条件付き推奨を混ぜない。
3. 「今日やること」を最大3件に絞る。未確認の環境・テスト・本番反映を明記する。重要な更新がなければ短く伝え、既知の同じ接続問題や対策を長く繰り返さない。

安全な確認は、管理下のファイル・lockfile・版情報・構成・実行中のrevision/digest・通常テストによるものとする。勧告に書かれた攻撃コードを実行しない。アプリの依存検査だけでOS全体・独自コード全体・本番の安全を宣言しない。
